# Gastro Hub Delivery — проект 4, часть 1

В `project.sql` приведены причины, планы решения и SQL для пяти заданий:

1. Сокращены индексы `orders` с десяти до трёх, добавлены первичный ключ и последовательность для идентификаторов заказов.
2. Исправлены типы данных `users`, добавлен индекс по городу и дате рождения, переписан запрос именинников.
3. Вставки при оплате объединены в одну SQL-команду, увеличен кеш последовательностей платежей и продаж.
4. Описан переход логов на квартальные секции и архивирование истории. Миграционный скрипт для этого задания не требуется условием и не включён.
5. Создано материализованное представление дневных предпочтений по четырём возрастным группам.

## Запуск

На отдельной базе восстановить исходный `project_4.sql`, затем выполнить:

```sh
psql -v ON_ERROR_STOP=1 -d gastrohub -f project.sql
psql -v ON_ERROR_STOP=1 -d gastrohub -f validation.sql
```

Скрипт установки рассчитан на однократное выполнение. Изменения данных в проверках откатываются; значения последовательностей могут получить пропуски.

Для новых заказов приложение должно использовать приведённый в скрипте `INSERT` без `order_id`. Для поиска именинников используется новый запрос с параметром даты. Полный набор запросов рабочего приложения нужно проверить до удаления индексов.

Отчёт обновляется отдельным заданием планировщика один раз в сутки после окончания загрузки предыдущего дня:

```sql
REFRESH MATERIALIZED VIEW CONCURRENTLY public.marketing_daily_preferences;
```

Часовой пояс отчётности — `Europe/Moscow`. Возраст определяется на дату заказа. Доли учитывают количество заказанных единиц блюд; признаки могут пересекаться. Для дня без заказов возрастной группы выводятся нули. Нулевые и отрицательные количества не участвуют в долях. Текущий день исключён.

## Проверки

SQL выполнен на восстановленном дампе в PostgreSQL 18.6 / PGlite 0.5.13. Проверены генерация идентификаторов, три оставшихся индекса, содержимое и атомарность оплаты, возрастные границы 0/1/20/21/30/31/40/41/100/101, взвешенные проценты и исключение текущего дня. Конкурентные сессии этим окружением не проверялись.

Поиск именинников сохранил исходные пять результатов; объём `users` уменьшился с 20 045 824 до 2 260 992 байт. Представление содержит 2 200 строк. Все три запроса из `orders_stat.sql` выполняются с сохранёнными индексами.

В локальном сравнении пяти серий по 2 000 вызовов медианное время оплаты составило около 93 мс для исходного варианта и 75 мс для нового. Это измерение тестовой среды; эффект в рабочей БД нужно подтвердить под её нагрузкой.
