# Gastro Hub

Самостоятельный проект второго модуля «Применение баз данных».
`project.sql` создаёт и заполняет четыре таблицы, представление и материализованное представление, затем выполняет все семь аналитических заданий. `validation.sql` содержит дополнительные проверки без изменения данных.

## Запуск

Нужны PostgreSQL 15 или новее и установленное на сервере расширение PostGIS.
Используйте отдельную пустую базу. Сначала восстановите оригинальный дамп из задания, затем запустите решение и проверки.

Для текстового дампа распакуйте [sprint2_sql_dump.zip](https://code.s3.yandex.net/data-analyst/SQL_dev/sprint2_sql_dump.zip) и выполните:

```bash
createdb -U postgres gastro_hub
psql -X -v ON_ERROR_STOP=1 -U postgres -d gastro_hub -f sprint2_sql_dump.sql
psql -X -v ON_ERROR_STOP=1 -U postgres -d gastro_hub -f sprint_2/project.sql
psql -X -v ON_ERROR_STOP=1 -U postgres -d gastro_hub -f sprint_2/validation.sql
```

Если текущий каталог уже `sprint_2`, уберите префикс `sprint_2/` в последних двух командах. Для архивного дампа `sprint2_dump.sql` из задания используйте pgAdmin Restore или pg_restore; расширение файла не определяет его внутренний формат.

Исходный дамп уже создаёт схемы `cafe`, `raw_data` и расширение PostGIS в `public`. Решение не удаляет таблицы и не меняет исходные данные. Создание и заполнение новых таблиц выполняются в одной транзакции. Для повторного запуска всего проекта нужна новая база с исходным дампом: скрипт намеренно не уничтожает ранее созданные объекты.

## Решения и допущения

- `restaurants` и `managers` получают случайные UUID v4 через `gen_random_uuid()`. Продажи и периоды работы имеют составные первичные ключи, как в условии. Внешние ключи сохраняют связи между таблицами.
- Тип заведения хранится как `cafe.restaurant_type`, меню — `jsonb`, положение — `geometry(Point,4326)`. В точке сначала указана долгота, затем широта. Профиль заведения и меню переносятся без произвольного выбора из конфликтующих строк.
- Менеджер определяется парой имя/телефон, чтобы не объединять однофамильцев. В исходных данных 20 уникальных имён и 20 пар имя/телефон, каждому имени соответствует один телефон.
- Для каждой пары ресторан/менеджер по условию есть один непрерывный период. Начало и конец — включительные границы наблюдений `MIN(report_date)` и `MAX(report_date)`. Это границы данных, а не предположение о трудоустройстве до/после периода наблюдения.
- Средний чек в отчётах — арифметическое среднее дневных средних чеков. Числа заказов в источнике нет, поэтому взвешенное среднее восстановить нельзя.
- Задание 1 использует `ROW_NUMBER` для ровно трёх заведений каждого типа. Равенство разрешается названием. Ранжируется неокруглённое среднее.
- В задании 2 `LAG` возвращает среднее предыдущего года. В данных все заведения представлены во всех годах 2017–2023; 2023 исключён. Первый год остаётся с NULL, процент считается до округления средних, деление на ноль защищено.
- Число смен менеджера — число периодов минус первое назначение. Оно отдельно проверено по фактическим переходам менеджера между соседними датами источника.
- В заданиях 4–5 рассматривается только раздел меню `Пицца`. Сохраняются все пиццерии с максимальным количеством пицц и все пиццы с одинаковой максимальной ценой. Цены сравниваются как числа.
- В задании 6 сравниваются уникальные пары заведений одного типа; расстояние считается через `geography` в метрах. Возвращается одна глобально ближайшая пара, а не по одной на каждый тип.
- В задании 7 `LEFT JOIN` учитывает районы с нулём заведений, `ST_Covers` включает точки на границе. При равном количестве выбирается район по названию; максимальный идёт первым, минимальный вторым. В источнике все 80 заведений распределены между 10 районами без повторного попадания.

## Проверка на исходном дампе

Весь оригинальный текстовый дамп и весь итоговый SQL выполнены в PostgreSQL 18.6 через PGlite 0.5.12 с настоящим расширением PostGIS 3.6.2 (`@electric-sql/pglite-postgis` 0.2.12). Для восстановления не заменялись геометрия и пространственные функции заглушками. Запуск в нативном PostgreSQL 15, Docker или pgAdmin отдельно не выполнялся.

| cafe.sales | 204480 |

Проверено восстановление всех восьми исходных полей через новые таблицы и периоды работы: `EXCEPT ALL` в обе стороны не выявил потерь, лишних строк или искажений. Меню совпадают, пересечений периодов менеджеров нет, геометрии валидны и имеют SRID 4326. Проверены отказы ограничений для дубля заведения, отрицательного среднего чека, отсутствующего внешнего ключа, массива вместо объекта меню, неизвестного типа заведения и неправильного SRID.

Все семь отчётов сопоставлены с независимым расчётом из оригинального дампа: денежные показатели — Python Decimal, геодезическое расстояние — GeographicLib, попадание в районы — Shapely по исходным WKB-полигонам.

Контрольные результаты:

- Топ заведений — 12 строк; годовой отчёт — 480 строк за 2017–2022, первые значения предыдущего чека у 80 заведений равны NULL.
- Три первых заведения по числу смен менеджеров — Deli Delight, Grill & Grains и Pasta Palace: по 7 смен.
- Максимум 12 пицц у Slice of Rome, «Пицца Парадизо» и «Тосканский Трактир»; отчёт самых дорогих пицц содержит 20 строк.
- Ближайшая пара одного типа — Cafe Comfort и Grill & Grains: 63.66510867 м.
- Больше всего заведений в Хамовниках — 16, меньше всего в Мещанском районе — 2.

Материализованное представление — снимок данных на момент создания. После новых продаж его нужно обновить командой `REFRESH MATERIALIZED VIEW cafe.yearly_average_checks;`.
